# Implementation Plan: Welcome Screen

**Branch**: `2026-10-14-welcome-screen` | **Date**: 2026-10-14 | **Spec**: [spec.md](spec.md)

## Summary

A company carries `is_welcome_screen_pending`, set to true when `CreateCompany` runs. A middleware
on the signed in routes sends the user of a pending company to `GET welcome`. Its button sends
`PUT welcome`, which calls the `DismissWelcomeScreen` action, sets the flag to false and redirects
to home. Choices are argued in [research.md](research.md).

**Structure Decision**: the controller sits at the root of `App` beside `Auth` and `Settings`,
since the screen belongs to neither; view and view model mirror it. The new view lives in
`resources/views/app/`, so it does not collide with the framework placeholder
`resources/views/welcome.blade.php` that home still renders.

## Behavior

1. `CreateCompany` passes `is_welcome_screen_pending => true`. The column defaults to false, so
   seeded and factory companies are not pending unless a factory state says so.
2. `RedirectToWelcomeScreen` lets the request through when there is no user or the company is not
   pending; otherwise it redirects to `welcome.index`. It is added to `home.index` and to the three
   `auth` groups of `routes/web.php`. It is never on `routes/auth.php`, so the email confirmation
   notice, the confirmation link and signing out keep working (FR-003).
3. `WelcomeController@index` redirects to home when the company is not pending (FR-007), otherwise
   renders the view with `WelcomeViewModel`.
4. `WelcomeController@update` calls `DismissWelcomeScreen(user:)` and redirects to home.
5. `DismissWelcomeScreen` sets the flag to false on the user's own company and logs
   `WelcomeScreenDismissed` only when the flag was true, so a second tab does not log twice.

[contracts/routes.md](contracts/routes.md) lists the two routes; [data-model.md](data-model.md)
the column.
